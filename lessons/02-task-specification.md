# Prompt를 작업 명세로 발전시키기

## 짧은 요청의 한계

다음 요청은 목표를 전달하지만, 구현에 필요한 결정을 대부분 Agent에게 남깁니다.

> Task 완료 기능하고 삭제 기능 만들어줘. UI도 보기 좋게 수정해줘.

Agent는 기존 기술을 유지할지, API를 바꿔도 되는지, 테스트를 작성할지, 어디까지 UI를 고칠지 추측해야 합니다. 잘 작동하는 Agent라도 그 추측이 팀의 의도와 일치한다고 보장할 수는 없습니다.

## 작업 명세의 구성

명세는 자연어 프롬프트의 길이가 아니라, 성공 여부를 판단하는 데 필요한 정보를 전달하는 수단입니다.

### Goal

무엇을 달성해야 하는지 한두 문장으로 설명합니다.

### Scope

수정해도 되는 영역과 이번 작업에서 건드리지 말아야 할 영역을 구분합니다.

### Constraints

기술 선택, 하위 호환성, 보안 또는 제품 규칙처럼 지켜야 할 조건을 씁니다. 제약은 이유가 분명하고 확인 가능해야 합니다.

### Requirements

사용자에게 보이는 동작을 구체적인 항목으로 나눕니다. 모호한 “잘 동작하게” 대신 입력, 성공 상태, 오류 상황을 설명합니다.

### Verification

테스트나 수동 점검 등 완료 여부를 확인할 방법을 명시합니다. 검증 방법은 요구사항과 연결되어야 합니다.

### Done criteria

어떤 상태가 되어야 작업이 완료인지 정의합니다. 예를 들어 기존 기능 유지, 테스트 통과, 브라우저 동작 확인, 변경 내역 보고 등을 포함할 수 있습니다.

## 작업 명세의 예시 틀

```text
목표
  달성하려는 사용자 가치 또는 기능

범위
  수정 가능한 파일 또는 영역

제약
  유지할 기술, 호환성, 금지할 변경

요구사항
  관찰 가능한 기능 동작과 오류 처리

검증 방법
  실행할 테스트와 수동 확인

완료 조건
  완료를 판단할 기준과 결과 보고 항목
```

## 좋은 명세의 성질

- **검증 가능하다:** “깔끔하게”보다 구체적인 사용자 동작과 기준을 쓴다.
- **필요한 자유를 남긴다:** 모든 구현 단계를 지시하지 않고 목표와 경계에 집중한다.
- **기존 맥락을 존중한다:** 이미 있는 API나 구조를 바꾸는 작업은 그 사실을 명시한다.
- **위험에 비례한다:** 작은 문서 수정에는 짧게, 넓은 구조 변경에는 더 상세하게 작성한다.

명세가 너무 세세하면 Agent가 더 나은 구현을 제안할 여지를 줄이고, 내용이 모호하면 의도하지 않은 선택을 늘릴 수 있습니다. 요구사항과 제약의 균형은 실험과 검토를 통해 조정합니다.

## 다음 실험에서 확인할 것
