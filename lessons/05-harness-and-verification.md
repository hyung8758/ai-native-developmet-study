# Harness와 검증 루프

## Harness란

Harness는 Agent가 목표에 도달하도록 돕고, 결과를 확인할 수 있게 둘러싼 작업 환경을 가리킵니다. 프로젝트 규칙 파일 하나를 뜻하지 않습니다. 작업 맥락, 도구, 권한 범위, 테스트, 피드백 절차가 함께 작동합니다.

```text
목표와 맥락
     ↓
규칙과 도구 ──→ Agent의 탐색·구현
                    ↓
             테스트와 검증
                    ↓
               피드백·수정
                    ↺
```

## Harness의 구성 요소

- **맥락:** README, 소스, 설계 문서, 작업 명세
- **규칙:** 수정 범위, 기술 제약, 프로젝트 관례
- **도구:** 셸, 버전 관리, 테스트 실행기, 브라우저 등
- **권한 경계:** Agent가 읽거나 변경할 수 있는 범위
- **검증:** 자동 테스트와 필요한 수동 확인
- **피드백:** 실패의 원인을 전달하고 수정 여부를 확인하는 과정

구성은 프로젝트와 작업 위험에 맞춰 선택합니다. 작은 변경에 무거운 절차를 추가하면 작업을 방해할 수 있고, 넓은 변경에 검증 기준이 없으면 결과를 믿기 어렵습니다.

## 결과 상태를 확인하기

Agent가 “완료했습니다”라고 보고하는 것은 결과에 대한 주장입니다. 실제 완료 여부는 저장소의 변경 내용, 테스트 결과, 사용자 동작으로 확인해야 합니다.

예를 들어 기능 작업 뒤에는 다음 근거를 확인할 수 있습니다.

- 요구사항과 연결된 테스트가 있는가?
- 기존 테스트도 계속 통과하는가?
- 브라우저에서 주요 동작이 확인되는가?
- diff에 요청하지 않은 변경이 들어 있지 않은가?
- 실패나 미확인 항목이 명시되었는가?

자동화할 수 있는 확인은 반복 실행할 수 있게 만들고, 자동화하기 어려운 사용성이나 제품 판단은 사람이 검토합니다.

## 테스트와 평가

테스트는 프로그램 동작이 기대한 조건을 만족하는지 확인합니다. Agent 실험의 평가는 테스트 통과 여부뿐 아니라 요구사항 준수, 변경 범위, 회귀, 작업 중 사람의 개입 등을 포함할 수 있습니다.

실험을 비교하려면 결과를 같은 기준으로 기록해야 합니다. 예를 들어 수정 파일 수, 누락 요구사항, 검증 성공 여부, 불필요한 변경, 사람의 개입 횟수를 관찰할 수 있습니다. 한 번의 실행만으로 일반적인 성능을 단정하지 말고, 환경과 결과를 함께 해석합니다.

## 신뢰할 수 있는 반복 루프

```text
작업 명세
  → Agent가 맥락을 확인하고 계획
  → 구현
  → 테스트와 UI 확인
  → 실패 원인 수정
  → diff와 결과 검토
```

이 루프는 Agent가 무한히 수정하도록 두라는 뜻이 아닙니다. 제한된 범위에서 검증하고, 실패 원인과 남은 위험을 드러내며, 사람이 종료 판단을 내릴 수 있도록 해야 합니다.
