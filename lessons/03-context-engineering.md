# Context Engineering

## Agent에게 프로젝트 맥락이 필요한 이유

작업 목표가 명확해도 Agent가 프로젝트의 구조와 관례를 모르면 잘못된 가정을 할 수 있습니다. 처음 합류한 개발자가 실행 방법, 테스트 방식, 코드 구조를 알아보는 것과 비슷합니다.

맥락이 없을 때 Agent는 다음을 추측할 수 있습니다.

- 어떤 기술과 패턴을 이미 쓰고 있는가?
- 어디에 코드를 추가해야 하는가?
- 테스트는 어떻게 실행하는가?
- 호환성을 지켜야 할 API가 있는가?
- 특정 디렉터리나 파일을 수정해도 되는가?

## Prompt Engineering과 Context Engineering

Prompt Engineering은 요청을 어떻게 표현할지에 초점을 둡니다. Context Engineering은 Agent가 작업 중 판단에 활용할 수 있는 전체 맥락을 어떻게 구성할지 다룹니다.

```text
Prompt: 이번 작업에서 무엇을 해 달라고 할까?

Context: Agent가 그 일을 이해하고 수행하는 데 어떤 정보가 필요한가?
```

Context에는 요청문뿐 아니라 프로젝트 문서, 소스 코드, 규칙, 도구, 작업 상태, 테스트 결과 등이 포함될 수 있습니다.

## 필요한 맥락을 찾기 쉽게 만들기

모든 문서를 매 요청에 복사해 넣는 것이 좋은 해결책은 아닙니다. 중요한 정보가 너무 많으면 관련 내용을 찾기 어렵고, 중복되거나 오래된 지침이 충돌할 수 있습니다.

프로젝트 맥락은 정보의 목적에 맞게 배치합니다.

- 프로젝트 소개와 실행법: `README.md`
- 지속적으로 적용할 작업 규칙: `AGENTS.md`
- 특정 반복 절차: Skill 문서와 필요한 보조 자료
- 실제 동작과 현재 구조: 소스 코드와 테스트
- 이번 일의 목표와 범위: 작업별 명세

파일 이름과 위치가 명확하고 내용이 최신이면, Agent가 필요한 맥락을 스스로 찾기 쉬워집니다.

## 지속 맥락과 작업별 맥락

프로젝트마다 항상 적용되는 규칙과 한 번의 작업에만 필요한 정보는 구분하는 편이 좋습니다.

| 정보 종류 | 예시 | 적절한 위치 |
| --- | --- | --- |
| 매 작업에 적용되는 규칙 | 테스트 명령, 디렉터리 관례 | `AGENTS.md` 또는 프로젝트 문서 |
| 반복되는 절차 | API 변경 후 검증 순서 | Skill |
| 이번 요청의 목표 | 완료 기능 추가, 특정 파일 범위 | 작업 명세 |
| 현재 상태와 근거 | 구현 코드, 테스트 결과 | 소스 코드와 실행 결과 |

## 맥락 품질을 관리하기

맥락은 많을수록 좋은 것이 아니라 정확하고, 필요한 시점에 찾을 수 있고, 서로 일관되어야 합니다. 잘못된 실행 명령이나 이미 폐기된 규칙은 Agent를 오히려 잘못된 방향으로 이끕니다. 문서는 코드와 함께 갱신하고, 규칙은 실제로 필요한 수준만 유지해야 합니다.

## 다음 실험에서 확인할 것

실습에서는 Agent에게 제공되는 프로젝트 안내와 규칙을 단계별로 바꿔 봅니다. 어떤 맥락이 추측을 줄였는지, 불필요하거나 모순된 맥락은 없었는지 결과와 함께 기록합니다.
